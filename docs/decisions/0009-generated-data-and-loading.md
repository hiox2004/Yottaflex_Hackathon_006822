# 0009. Generated data policy and database loading
Date: 2026-11-14 · Status: Accepted

## Context
The database runs in Docker and is never committed. The brief wants CSV, JSON and SQL seed data, a manifest, a validation
summary and a reproducibility proof, and a reviewer should be able to inspect results without running anything.

## Decision
- Database files and volumes are never in git. Data is generated by the seeded generator (seed `20261022`) and loaded
  with one command: `python -m integrity.dbload --scale starter|full`. It drops the `public` schema, applies
  `database/schema.sql`, then runs `data/<scale>/seed.sql`.
- Committed: `data/starter/` (small, shows the deliverables), the full-scale manifest with SHA-256 checksums and the
  validation summary.
- Not committed: full-scale bulk files and ground truth for the full scale; they are regenerated bit-for-bit from the seed.
- Case IDs use `CAS-` (decision 0005 accepted).
- Container start runs `python -m integrity.cli bootstrap --scale full`: it generates `data/full/` only when `seed.sql`
  or `manifest.json` is missing, and loads only into an empty database (existing data is never wiped on restart).

## Why
Keeps the repo small and avoids binary or bulky files, while the checksums in the manifest let anyone prove a regenerated
dataset is identical. One loader command keeps setup simple and the same for dev, tests and the demo.

## Alternatives considered
Mounting the schema into the Postgres init directory (a second loading path to maintain); committing the full dataset
(10,000-row files, noisy diffs).

## Consequences / revisit when
Reviewers who want the full data must run the generator. If the starter files grow large, move them out of git too.
